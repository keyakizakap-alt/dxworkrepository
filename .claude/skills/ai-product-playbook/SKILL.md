# AI プロダクト実装プレイブック

CHIGIRI Beauty 系 3 本 / ニュアンス税関 / オシ・カレ / こいのかたち / 引っ越しアプリを
作る過程で確定した判断基準。**毎回ゼロから設計判断をやり直さないため**にある。

新規に書くときは下の 8 原則をそのまま制約として使う。既存コードを触るときは、
その repo が既にこの形になっているかを先に確認し、**ずれていても勝手に作り替えない**
（動いているアプリの挙動を変えない。原則から外れている箇所は指摘だけして判断を仰ぐ）。

---

## 8 原則

1. **LLM に意思決定をさせない。** 選定・除外・順位づけ・可否判定は決定論的な純関数で行い、
   LLM の担当は「確定した結論の説明文」だけに限る。これで再現性・カタログ外の出力防止・
   AI 障害時の継続稼働が同時に手に入る。
2. **フェイルオープンさせない。** 検査に失敗したのに「安全です」と返すのが最悪の失敗。
   判定不能は必ず安全側（遮断 / 警告 / 未検査の明示）に倒す。`200 OK で全部 green` は禁止。
3. **外部送信の経路は 1 本にし、型で縛る。** 外部 API を呼ぶ関数に「許可証」型を必須引数として
   要求し、その型はポリシー判定モジュールでしか生成できないようにする。文章の約束ではなく
   コンパイルエラーで守る。コストの歯止めも同じ関門に載せる。
4. **キーが無くても全機能が動く。** `API_KEY` 未設定はエラーではなくデモ/決定論モードへの分岐。
   発表当日にキーが死んでも製品は動く。
5. **LLM 出力は検証してから使う。** JSON parse → スキーマ（Zod）→ 許可 ID 照合 → 禁止表現検査。
   1 つでも落ちたら出力ごと破棄して決定論的応答へ。失敗は隠さず UI に理由を出す。
6. **公開 API は入口で固める。** Content-Type 強制・本文サイズ上限・IP レート制限・
   エラー詳細を返さない。認証なしで有料 LLM を呼ぶ口は、放置すると残高が焼かれる。
7. **推測した値で埋めない。** 在庫・価格・送料・出典・検証状態が未確認なら `null` と
   「未確認」バッジ。それらしい数字で埋めた瞬間、画面の合計額が嘘になる。
8. **秘密は `server-only` の内側だけ。** `NEXT_PUBLIC_` を付けない。署名鍵が本番で未設定なら
   起動時に落とす（黙って一時鍵で動かすと、再現性のない不具合になる）。

## 着手フロー

```
市場・前提の確認 → 「AI を抜いても成立するか」ゲート → 決定論コアの設計
  → 境界（LLM を呼ぶ 1 点）の決定 → API 入口ガード → デモモード
  → 品質ゲート（lint/typecheck/test/build/audit）→ デプロイ → README
```

- **「AI を抜いても成立するか」ゲート**：抜いて成立するなら AI は要らない。抜くと何も残らない
  一点を特定し、そこにだけ LLM を置く。この問いを最初に通すと後工程の判断がほぼ自動で決まる。
- **決定論コアを先に書く。** LLM を後から足す。逆順にすると、コアが LLM に依存して剥がせなくなる。
- 未確定事項は**推測で埋めず、人手の手順（ワークシート等）を用意する**。
  外部到達性の無い環境で「確認していないものを確認したことにする」のが最も危険。

## やらないこと

- 動作中のアプリのロジック・API 契約・保存形式を、この原則に合わせるためだけに書き換える
- 口コミ本文・商品画像など**他者の著作物を自分の配信元へ複製**する
- スクレイプ禁止のデータを取得する（架空データを自作し、架空であると明記する）
- 個人アカウントの分析・スコアリング、説教口調の出力
- 薬機法・医療の境界を越える表現（診断・治療・効果保証）
